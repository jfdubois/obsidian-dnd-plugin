# Catalog Server — Update and Rollback Procedure

Operational procedures for updating catalog revisions, rolling back to previous revisions, and rolling back the server container image.

## 1. Update to a New Catalog Revision

Catalog revisions are immutable files generated by the catalog builder. Updating the server means replacing the host-side catalog directory and restarting the container so the read-only mount reflects the new data.

### Step 1 — Build the new catalog

Run the catalog builder to produce a new revision tree. The output must contain at minimum:

```
catalog/v1/current.json          # Pointer to the latest revision
catalog/v1/revisions/<tag>.json  # Immutable revision payloads
```

### Step 2 — Verify the new catalog on disk

```bash
ls catalog/v1/current.json
ls catalog/v1/revisions/
```

Confirm `current.json` points to the revision you intend to deploy.

### Step 3 — Restart the container

The catalog volume is mounted read-only (`:ro`). Replacing the host directory contents is sufficient; no rebuild is needed.

```bash
docker compose restart catalog-server
```

### Step 4 — Verify with the health check

```bash
curl http://localhost:8080/health
# {"status":"healthy"}

# Confirm the new revision is served
curl http://localhost:8080/catalog/v1/current.json
```

The Docker healthcheck probes `/health` every 30 seconds. After restart, the container should report healthy within one interval.

## 2. Rollback to a Previous Catalog Revision

Because revisions are immutable files, rolling back means restoring the previous catalog directory and restarting the container.

### Option A — Restore from backup (recommended)

Before each update, back up the current catalog directory:

```bash
cp -r catalog catalog.bak.$(date +%Y%m%d%H%M%S)
```

To roll back:

```bash
# Remove the failed catalog
rm -rf catalog

# Restore the most recent backup
mv catalog.bak.<timestamp> catalog

# Restart the server
docker compose restart catalog-server
```

### Option B — Edit current.json to point to an older revision

If the revision files themselves are intact and only `current.json` was updated incorrectly:

```bash
# Edit catalog/v1/current.json to reference the previous revision tag
# Then restart
docker compose restart catalog-server
```

### Verify rollback

```bash
curl http://localhost:8080/health
curl http://localhost:8080/catalog/v1/current.json
```

## 3. Rollback the Server Container (Docker Image)

If the nginx configuration or Docker image itself is faulty, roll back the container image.

### Option A — Rebuild from a known-good Dockerfile tag

```bash
# Tag the current image before rebuilding
docker tag catalog-server catalog-server.bak.$(date +%Y%m%d%H%M%S)

# Rebuild from the previous Dockerfile
docker compose build catalog-server
docker compose up -d catalog-server
```

### Option B — Restore a tagged image

If you tagged images before each deployment:

```bash
# Stop current container
docker compose down

# Restore the previous image
docker tag catalog-server.bak.<timestamp> catalog-server

# Start with the restored image
docker compose up -d
```

### Verify container rollback

```bash
docker compose ps catalog-server
# State should be "healthy"

curl http://localhost:8080/health
# {"status":"healthy"}
```

## 4. Safety Considerations

### Read-only catalog mount

The catalog volume is mounted with the `:ro` flag in `docker-compose.yml`:

```yaml
volumes:
  - "${CATALOG_DATA_PATH:-./catalog}:/usr/share/nginx/html/catalog:ro"
```

The container **cannot** modify catalog files. All updates and rollbacks must occur on the host filesystem before restarting the container.

### Immutable revisions

Files under `catalog/v1/revisions/` are immutable once published. They are served with `Cache-Control: public, max-age=31536000, immutable`. Never overwrite or delete a revision file; always publish a new revision tag.

### Directory traversal protection

The nginx configuration blocks `..` sequences in catalog paths. Do not disable this protection.

### No built-in authentication

The catalog server has no authentication. If exposed beyond your local network, place a reverse proxy with authentication in front of it.

## 5. Health Check Reference

| Endpoint | Method | Response | Purpose |
|---|---|---|---|
| `/health` | GET | `{"status":"healthy"}` | Container liveness probe |
| `/catalog/v1/current.json` | GET | JSON pointer | Verify active revision |

The Docker healthcheck uses `wget` (available in `nginx:alpine`):

```yaml
healthcheck:
  test: ["CMD-SHELL", "wget --no-verbose --tries=1 --spider http://localhost:8080/health || exit 1"]
  interval: 30s
  timeout: 10s
  retries: 3
  start_period: 5s
```

Always verify the health endpoint after any update or rollback before relying on the server.
